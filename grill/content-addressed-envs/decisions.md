# Environnements adressés par leur contenu : décisions

- **Un principe commun**: ce qu'un layer construit est nommé par ce qui le définit, rangé dans les caches d'errand, jamais modifié une fois construit. Un ADR pour tous les layers qui construisent ( Micromamba/Conda, Uv, Venv `create`, Apptainer/Docker/Podman avec `recipe`, disque Windows ), Micromamba implémenté d'abord.
- **Externe ou à errand**: un layer qui ne fait que nommer ( `name` seul, `image` sans `recipe` ) est à l'utilisateur, jamais construit ni jugé ; un layer qui déclare son contenu est à errand. Plus d'adoption pour ces layers.
- **Identité = un lock versionné**: `errand-envs.lock` dans le projet, par env et par plateforme ; l'identité d'un env est le hash de son lock ; le hash de la déclaration, noté dans le lock, dit seulement quand résoudre à nouveau. `errand setup --update` re-résout volontairement.
- **Un store par machine**: `<cache du Ssh>/envs/…`, partagé entre projets, `pkgs_dirs` sur le même système de fichiers ; un env part quand aucun projet enregistré ne le déclare plus et qu'il n'a pas servi depuis N jours.
- **Éditables dans un overlay**: un venv `--system-site-packages` par projet et par env, dans `<outputs>/caches/build/<env>/develop`, `develop = [ … ]` installé `-e --no-deps`. Hugo veut que les dépendances des paquets liés soient dans l'env micromamba, pas dans l'overlay ( round 2 ).
- **Dépendances des paquets liés dans l'env**: `[project].dependencies` ( extras compris ) et `[build-system].requires` des chemins de `develop` sont ajoutés à la déclaration de l'env, en pip par-dessus la partie conda ; les paquets liés entre eux sont exclus ; une dépendance voulue de conda-forge se déclare dans `packages`.
- **Usage à la main**: `name` n'est qu'une étiquette ; `errand shell --env X` et `errand python --env X` ; errand n'écrit rien dans le root prefix de l'utilisateur ; le CLAUDE.md global est réécrit en conséquence.
- **Env modifié à la main**: détecté par le stamp, signalé, **refus de continuer**, avec la proposition d'ajouter ( ou retirer ) dans la déclaration les paquets changés ; la reconstruction se fait dans un nouveau répertoire ( détails au round 3 ).
- **Résolution sur la machine qui construit**, avec ses vrais paquets virtuels. Hugo veut que le lock dise « tout ce qui a de l'influence » sur la machine ( règle au round 3 ).
- **Un `errand-envs.lock` unique** en yaml à la racine ; partie pip par uv ( `--no-deps`, `--require-hashes` ).
- **Images et uv**: les images ont pour identité le hash de la déclaration complète ( `.def` + fichiers de `%files`, Dockerfile + contexte ), `image` facultatif ( alias ), le record garde le digest obtenu ; Uv prend `uv.lock` comme identité quand il existe.
- **Ce qui influence la résolution**: un lock garde, par résolution, la plateforme et la présence de `__cuda`, et les contraintes de ses paquets sur les paquets virtuels ( lues dans la solution ) ; une machine réutilise une résolution quand elle a la même présence et satisfait ses contraintes, sinon elle résout et ajoute la sienne ; `cuda = False` force le CPU. Côté pip, les hashes de toutes les roues de chaque version. La compute capability, MPI, les pilotes : notés dans le record, hors identité.
- **Refus devant un env modifié**: comparaison au lock, refus de lancer, différence affichée et lignes de déclaration proposées ( errand n'édite pas `errand-envs.py` ) ; déclaration changée → nouvel env à côté ; `errand setup --force` → reconstruit depuis le lock dans `<hash>-2` ; `--no-setup` lance quand même.
- **micromamba d'errand**: fetché et épinglé dans `<cache>/micromamba/<version>`, `pkgs_dirs` dans le store ; `executable` pour un site qui impose le sien ; `Conda` seulement pour les envs externes.
- **Envs existants**: aucune reprise ; les anciens ( `~/.mamba/envs/…` ) restent à Hugo, signalés une fois par `errand envs`.
- **Ménage du store**: un env déclaré par un projet enregistré ne part jamais seul ; sinon 30 jours sans usage ( 7 sur machine partagée ) ; `errand caches` le montre et le retire ; les paquets que plus aucun env ne lie partent avec.
- **Windows**: une image de base partagée entre projets, nommée par le hash de ce qui la définit ( ISO, index, msvc ), et un overlay qcow2 par projet.
- **Venv**: `create`, `requirements` et `pip` retirés ; `Venv( python = … )` ne nomme plus qu'un interpréteur externe. Les venvs à errand passent par `Uv`.
- **Machines sans internet**: pas de `build_on` pour les envs. Hugo : « que errand se charge de tous les downloads ( et donc les mette bien dans le cache, en non précieux ), avec transmission à un agent parent s'il n'y a pas internet » ( round 5 ).

## errand fait les téléchargements ( ADR à part )

- **Un proxy local servi par l'agent de la place**: en cache → servi ; internet ici → téléchargé, rangé, servi ; pas d'internet → une requête qui attend ( ADR 0035 ), la réponse HTTP suspendue jusqu'à ce qu'un agent la remplisse. Seul lien vivant : local. La résolution reste sur la machine qui construit ; les délais des outils sont relevés.
- **Réécriture des URLs des outils pilotés**: canaux micromamba, `--index-url` d'uv ( liens de PyPI réécrits ), miroir de registre pour apptainer ; pas d'interception TLS ; ce qu'errand ne pilote pas passe par `errand download`.
- **Cache par machine, non précieux**: `<cache>/downloads/<sha256>/<nom>` au format des caches d'errand ; parti après 14 jours sans usage ; immuables servis sans revalider, index revalidés après 1 heure, l'ancien servi ( et dit ) sans internet sur la chaîne. `errand.download` ( ADR 0013, données du projet ) inchangé.
- **Relais**: chaque agent qui relaie garde une copie non précieuse ; transport des agents ( ADR 0006 ) ; internet constaté ( essai court, gardé quelques minutes ) et déclarable ( `Ssh( internet = False )` ).
- **Deux ADR écrits ensemble**: « errand fait les téléchargements » ( amende 0013, ferme la question ouverte de 0035 ) et « les envs adressés par leur contenu » ; implémentation par les envs sur une machine connectée d'abord.
